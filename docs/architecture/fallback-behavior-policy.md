# Fallback Behavior Policy (No Speech Fabrication)

## Purpose

Fallback handling must preserve model autonomy. Runtime code may normalize transport payloads and emit diagnostics, but must not inject assistant/user wording that tells the model what to say.

## Allowed behavior

- Transport normalization markers that preserve message structure when source platforms omit text.
  - Example markers: `(image attachment)`, `[media message]`.
- Structured failure diagnostics in logs, events, and metadata.
- Deterministic technical error strings for tool/method failures (for example, HTTP status-based fetch errors).
- Recovery retries that replay existing transport-normalized user content.

## Disallowed behavior

- Injecting synthetic prompts such as "Runtime note..." that fabricate user or assistant speech.
- Canned conversational fallbacks from adapters/tooling such as "Something went wrong. Please try again." when generated by runtime fallback paths.
- Any fallback path that appends prescriptive assistant guidance ("say X", "ask for resend", etc.).

## Required behavior by failure class

- Attachment/vision failure:
  - Do not inject guidance text.
  - Optionally retry by replaying transport-normalized user content only.
  - Emit metadata diagnostics in the response payload.
- Tool or gateway method failure:
  - Return explicit technical diagnostics (status/code/details).
  - Do not wrap with conversational filler text.
- Input/adapter handler failure:
  - Emit channel diagnostics events and logs.
  - Do not auto-send synthetic chat replies.

## Diagnostics contract

- `AgentResponse.metadata.diagnostics.fallback` is used for transparent fallback metadata (code, strategy, attempts, final state).
- Channel adapters emit `channel.message.error` events with channel/message identifiers and error details.
